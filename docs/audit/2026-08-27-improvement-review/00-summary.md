# 12 个改进方向多角度审核 — 汇总报告

> **生成时间**：2026-08-27  
> **审核方法**：6 个并行子 agent，每个先读完整源码（平均 7-11 个文件）再从 7 维度评估  
> **范围**：上一轮我提出的 12 个性能/质量改进方向  
> **结论**：**12 个里 6 个不建议实施、3 个推荐简化版、2 个 P2、1 个分档实施**

---

## 0. 核心元认知

**我之前提的方向被批得最多的原因**（跨方向共性，#1/#2/#3/#6/#9 都有）：

1. **低估了"已有自适应性"**——这个项目经历过 P1/P2 批量修复（agent.md §10.13-10.15），很多"明显可优化"的点已经被动自适应了（滚动阈值按书长、prompt 截断保序、KB 快照隔离、温度退火 + 指数退避 + 429 退避三层、JSON 9 级修复、failure token 不计零等）
2. **低估了"重试链烧 token"风险**——任何 validate 阶段加严都可能让 LLM 反复触发完整重试链（每次重试真实扣费）
3. **低估了"prompt cache 稳定前缀"的脆弱性**——任何重新排序或条件注入都会击穿远端 KV cache（cache miss 比 cache hit 贵 2-3 倍）
4. **低估了"网文别名场景"的复杂度**——项目无 alias/canonical_name 系统，字符串包含对"小张/张铁柱/张哥"等多名场景漏检
5. **低估了"checkpoint 全量失效"的代价**——13 本老书要 backfill 几乎不可能

**这些反馈本身是有价值的**——说明这个项目远比表面看起来成熟，"性能还有空间"是真的，但空间不在我之前提的方向上。

## 3. #4 主动限流 — 分档推荐（用户实际场景价值最大）

**为什么单独拆**：9 个预设里只有 OpenAI 官方 + Anthropic 完整支持 header；DeepSeek 官方明确不支持；MiniMax/智谱/火山行为不稳定。**用户的 13 本书实际场景里这些端点占多数**。

### 档 A（先做，1-2 天）
- 探测端点 `POST /api/llm/probe-rate-limit`（照搬 `probe_thinking_params` 模式）
- 仅 OpenAI 协议（`provider=="openai"`）+ 非流式路径采集 `x-ratelimit-*` 头
- **不动** `chat_stream`（避开流式 `with_streaming_response` 重构对 H16 三分竞争的冲击）
- 落盘 `api.rate_limit_probe` 用于决策是否升级到档 B

### 档 B（对用户实际场景价值最大，2-3 天）
- 滑动窗口软限流（`(timestamp, prompt_tokens, completion_tokens)` 最近 60s 队列）
- **不依赖 header**，覆盖所有端点
- 实施简单：3 行起步
- 对 DeepSeek/智谱/火山/MiniMax 等无 header 端点特别有效

### 共同约束
- `asyncio.Semaphore` 不可收缩（Python 3.10+ 才有 `BoundedSemaphore` 但只是 release 校验）—— 要动态调窗只能依赖 `._value` 字段 hack
- `test_global_llm_sem.py:154` 强约束 `_value == 4` —— 任何动态 Sem 改动必须同步改测试
- Anthropic `anthropic-ratelimit-*` vs OpenAI `x-ratelimit-*` 前缀不同，抽象层必须双协议映射
- RateLimitState 必须在 AnalysisService 单例承载（每本书一个 LLMClient，重启即重置 stats）

## 4. 跨方向共性发现（重要）

### 4.1 已有自适应机制比想象的更完善

- ✅ 滚动总结首生成阈值按书长自适应（`pipeline.py:267-268`）
- ✅ momentum 归档触发器（`ROLLING_ARCHIVE_TRIGGER_COUNT=10` / `ROLLING_MOMENTUM_WINDOW=50`）
- ✅ prompt 正文超 3 万字符自动尾部保序截断（`prompt_builder.py:218-224`）
- ✅ KB 快照隔离（`memory_state.get_kb_snapshot` 三级缓存策略）
- ✅ 温度退火 + 指数退避 + 429 退避三层（`llm_client.py:1273/1357/1627/1659`）
- ✅ 9 级 JSON 修复链（含漏引号定向修复 + 全角归一）
- ✅ failure token 不计零（API 已扣费不能归零）
- ✅ PERF-2 关键词倒排索引（伏笔去重）

**结论**：项目的工程化深度远超"业余项目"层级，"明显可优化"的点基本已经做过。

### 4.2 4 处 Semaphore 全是局部实例（重要架构事实）

- `pipeline.py:441` 分析阶段
- `final_summary.py:525` 总结阶段（4 阶段 + 风格共用）
- `final_summary.py:1442` 复检局部
- `location_normalizer.py:553/613` 地点归一化
- **rolling client 走分析 sem，不走 final_summary 的 `_llm_sem`**

任何"全局限流"必须显式接入到 AnalysisService 单例层，不能直接 patch Semaphore。

### 4.3 13 本老书的 backfill 几乎不可能

所有"加新字段"的方案都面临同一困境：13 本已分析的 result.json 没有新字段。  
**要么**：重新跑（成本太高）  
**要么**：把新字段做成"可选"（前端容错降级显示"暂无"）  
**要么**：用程序化方式从老 result 推导（如 #12 方案 A 报告质量评分）

## 6. 用户最该先问自己的问题

在开始实施前，建议先回答：

1. **13 本书的总 API 成本是多少？预算阈值在哪？**（决定是否需要 #4 限流）
2. **质量下降（伏笔漏判、人物关系简化）可接受吗？**（决定 #7 网文专项的"分阶段"边界）
3. **断点续跑时混用主/次模型 result 接受吗？**（决定 #2 双层路由是否做）
4. **LLM-as-judge 偏差的容忍度？**（决定 #12 是否从程序化升到 LLM 评分）
